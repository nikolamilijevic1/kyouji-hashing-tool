1. PURPOSE
----------
This document verifies and documents the storage multiplication factors for
each storage tier used by the Hansken forensic platform. It ensures that
capacity planning reflects the correct number of data copies required for
processing, fault tolerance, and archiving — not just the raw input volume.

All calculations are grounded in official Apache Hadoop documentation,
Elasticsearch sizing best practices, and the Hansken architecture.


2. STORAGE TIERS IN SCOPE
---------------------------
Hansken uses four distinct storage tiers. Each has a different multiplication
factor and purpose:

  +------+-----------------------------------+----------------------------------+
  | Tier | Technology                        | Data Stored                      |
  +------+-----------------------------------+----------------------------------+
  |  A   | Apache Hadoop (HDFS)              | Raw forensic evidence images     |
  |  B   | S3 / Object Store                 | Derived trace data (OCR, parsed) |
  |  C   | Elasticsearch                     | Trace search indices             |
  |  D   | PostgreSQL                        | Project & preference metadata    |
  +------+-----------------------------------+----------------------------------+

These tiers correspond directly to the centralized storage architecture
documented in hansken_data_flow_hierarchy.md.


3. BASELINE INPUT ASSUMPTION
------------------------------
  Raw evidence input rate:  500 TB per year
  Analysis period:          Annual sizing (year 1 as baseline)
  Compression / encryption: Assumed applied before storage (Hansken stores
                            evidence in compressed, encrypted form in HDFS).
                            This document sizes AFTER compression; if
                            pre-compression sizing is needed, apply your
                            organization's evidence compression ratio first.

TIER A — APACHE HADOOP HDFS (Raw Forensic Evidence Images)
================================================================================

4A. WHAT HDFS STORES IN HANSKEN
---------------------------------
Per the official Hansken architecture documentation:
  "Apache Hadoop stores your images that are used as input for the
   extraction-process. For this we use the HDFS file system."
  — Source: https://learning.hansken.org/docs/architecture.html#hadoop

Raw evidence images (disk images, phone dumps, cloud archives) are uploaded
into HDFS and serve as the immutable source-of-truth for all extraction.
Extraction Workers read directly from HDFS. The data is never deleted after
extraction — it must remain for re-extraction, auditing, and chain of custody.


4B. REPLICATION FACTOR: WHY DEFAULT IS 3
------------------------------------------
The HDFS replication factor (RF) controls how many physical copies of each
data block exist across the cluster's DataNodes.

  Default Configuration Property:  dfs.replication = 3
  Source (Apache Official):         https://hadoop.apache.org/docs/current/
                                    hadoop-project-dist/hadoop-hdfs/hdfs-default.xml

WHY RF=3 IS THE HDFS DEFAULT — TECHNICAL JUSTIFICATION:

  The value of 3 is not arbitrary. It is the result of HDFS's rack-aware
  replica placement policy, which requires a minimum of 3 replicas to
  guarantee both node-level AND rack-level fault tolerance simultaneously:

    Replica 1:  Written to the local DataNode (or a random node in the
                writer's rack if writing from outside the cluster).
    Replica 2:  Written to a DataNode on a DIFFERENT rack.
    Replica 3:  Written to a DIFFERENT DataNode on the SAME rack as Replica 2.

  This placement means:
    - If 1 DataNode fails:  2 replicas remain (on 2 racks) → NO data loss.
    - If 1 entire rack fails: 1 replica remains on the other rack → NO loss.
    - During background re-replication (after a failure): 2 copies still
      exist at all times, preventing a "double failure" data loss window.

  Comparison of replication factors:
  +-----------+--------------------+------------------+---------------------+
  | RF Value  | Fault Tolerance    | Storage Overhead | Recommendation      |
  +-----------+--------------------+------------------+---------------------+
  | RF = 1    | None               |  1× raw size     | NOT suitable for    |
  |           | (single copy)      |                  | forensic evidence   |
  +-----------+--------------------+------------------+---------------------+
  | RF = 2    | Single node        |  2× raw size     | Minimal; vulnerable |
  |           | failure only       |                  | during re-repl.     |
  +-----------+--------------------+------------------+---------------------+
  | RF = 3    | Node + rack        |  3× raw size     | RECOMMENDED default |
  | (default) | failure            |                  | for forensic use    |
  +-----------+--------------------+------------------+---------------------+
  | RF = 5    | Very high          |  5× raw size     | Used in high-sec    |
  |           |                    |                  | financial/gov envs  |
  +-----------+--------------------+------------------+---------------------+

  For forensic evidence — which is legally critical, irreplaceable, and
  subject to chain of custody requirements — RF=3 is the minimum recommended
  setting. RF=2 is insufficient for a production forensic platform.

  ALTERNATIVE: Erasure Coding (Hadoop 3+)
    Hadoop 3 introduced Erasure Coding (EC) as an alternative to block
    replication. EC (e.g., RS-6-3-1024k) achieves ~50% storage overhead
    (vs. 200% for RF=3) with comparable fault tolerance for large files.
    EC is most effective for cold/archival data. It introduces CPU overhead
    during read and is NOT recommended as the default for hot active
    extraction data without careful testing.
    → Recommended: Use RF=3 for active evidence; evaluate EC for archival.


4C. HDFS STORAGE CALCULATION
-------------------------------
  Input (raw evidence per year):      500 TB
  Replication Factor:                 × 3
  Processing headroom (temp files,
    map/reduce shuffle, checksums):   + 25% of replicated volume
                                      (industry standard for HDFS overhead)
  ─────────────────────────────────────────────────────────────────────────
  HDFS replicated volume:             500 TB × 3       = 1,500 TB
  Processing overhead (25%):          1,500 TB × 0.25  =   375 TB
  ─────────────────────────────────────────────────────────────────────────
  TOTAL HDFS RAW CAPACITY REQUIRED:               ~1,875 TB (≈ 1.9 PB)
  ─────────────────────────────────────────────────────────────────────────

  Summary: Every 1 TB of raw evidence requires ~3.75 TB of HDFS raw disk
  capacity (multiplication factor: ×3.75).

TIER B — S3 / OBJECT STORE (Derived Trace Data)
================================================================================

5A. WHAT S3 STORES IN HANSKEN
-------------------------------
Per the official Hansken architecture documentation:
  "In Hansken it is used to store derived trace data, e.g. text extracted
   from an image using OCR, or text extracted from HTML."
  — Source: https://learning.hansken.org/docs/architecture.html#s3

Derived data is written by Extraction Workers after processing raw images.
Examples: OCR text, parsed HTML, file metadata, thumbnail previews,
communication content (chat logs, email bodies), extracted binary artifacts.

Derived data is typically SMALLER than the raw evidence. A representative
industry ratio is 5–15% of the raw input size, depending on evidence type.
For conservatism, this document uses 20% as the derived data estimate.


5B. REPLICATION / REDUNDANCY FACTOR FOR S3
--------------------------------------------
Hansken's S3 layer may be:
  a. A managed public cloud object store (AWS S3, Azure Blob, GCP GCS)
     → Typically 3× internal replication is handled transparently by
       the cloud provider. Standard-class storage = 11 nines durability.
  b. A self-hosted S3-compatible solution (e.g., MinIO, Ceph RGW)
     → MinIO in Erasure Code mode (default) uses a k+m parity model.
       MinIO default: EC:4 — requires 8 drives minimum; up to 4 drive
       failures tolerated. Effective storage overhead ≈ 2× raw size.

  For planning purposes, this document uses a conservative factor of 2×
  for self-hosted S3 (MinIO/Ceph), or 1× if using managed cloud storage
  (where replication is included in the service SLA).

  [PENDING — OI-1]: Confirm whether S3 is cloud-managed or self-hosted.
  See Section 9 (Open Items).


5C. S3 STORAGE CALCULATION
-----------------------------
  Derived data volume (20% of raw):  500 TB × 0.20    = 100 TB
  Self-hosted S3 replication factor: × 2
  Operational overhead (30%):        100 TB × 2 × 0.30 =  60 TB
  ─────────────────────────────────────────────────────────────────────────
  S3 base replicated volume:         100 TB × 2        = 200 TB
  Operational overhead:                                 +  60 TB
  ─────────────────────────────────────────────────────────────────────────
  TOTAL S3 CAPACITY REQUIRED (self-hosted):         ~260 TB
  TOTAL S3 CAPACITY REQUIRED (cloud-managed):       ~130 TB
  ─────────────────────────────────────────────────────────────────────────

  Summary: Derived data multiplication factor: ×2.6 (self-hosted) or
  ×1.3 (cloud-managed) relative to derived data volume.
  Relative to raw input: ×0.52 (self-hosted) or ×0.26 (cloud-managed).

TIER C — ELASTICSEARCH (Trace Search Indices)
================================================================================

6A. WHAT ELASTICSEARCH STORES IN HANSKEN
------------------------------------------
Per the official Hansken architecture documentation:
  "The Trace-service is responsible for CRUD operations on traces generated
   by Hansken, and stored in Elasticsearch."
  — Source: https://learning.hansken.org/docs/architecture.html#trace-service

Elasticsearch does NOT store the raw evidence or derived content files.
It stores structured JSON trace documents: metadata fields, extracted
attributes, communication records, file path hierarchies, timestamps, and
search-indexed fields that allow investigators to search across all evidence.

Elasticsearch index size relative to raw evidence depends heavily on:
  - The richness of the metadata extracted per file/artifact.
  - The number of traces generated (a single disk image may generate
    millions of trace records).
  - Elasticsearch field mappings (keyword vs. text, enabled fields).
  - A representative estimate for forensic trace indices is 10–30% of
    the raw input data size. This document uses 20% as the mid estimate.


6B. ELASTICSEARCH REPLICATION FACTOR
--------------------------------------
Elasticsearch achieves redundancy via index shard replicas, not block-level
replication. The standard configuration is:
  - 1 primary shard replica per primary shard (replica_count = 1)
  - This means every shard of data is stored twice (primary + 1 replica)
  - Effective storage multiplication factor for shards: × 2

Additional Lucene indexing overhead (inverted index, doc values, translog,
segment files) adds approximately 15–30% overhead above the raw JSON size.
For forensic trace data (text-heavy, many fields), 30% overhead is used.

  Total Elasticsearch multiplication factor:
    2 (primary + replica) × 1.30 (Lucene overhead) = ×2.60

  Best practice: Add 20–30% headroom to avoid hitting Elasticsearch low
  disk watermark (85% default), which blocks shard allocation and causes
  cluster instability.


6C. ELASTICSEARCH STORAGE CALCULATION
----------------------------------------
  Trace index data volume (20% of raw):    500 TB × 0.20    = 100 TB
  Shard replication (×2):                  100 TB × 2       = 200 TB
  Lucene overhead (×1.30):                 200 TB × 1.30    = 260 TB
  Safety headroom (25%):                   260 TB × 0.25    =  65 TB
  ─────────────────────────────────────────────────────────────────────────
  TOTAL ELASTICSEARCH CAPACITY REQUIRED:              ~325 TB
  ─────────────────────────────────────────────────────────────────────────
  [PENDING — OI-2]: Confirm trace index retention period. If Elasticsearch
  indices are retained for N years (not just active cases), this calculation
  must be multiplied by N. See Section 9 (Open Items).

  Shard sizing recommendation: Target 10–50 GB per primary shard.
  Too small = oversharding (cluster state overhead). Too large = slow recovery.

TIER D — POSTGRESQL (Project & Preference Metadata)
================================================================================

7A. WHAT POSTGRESQL STORES IN HANSKEN
---------------------------------------
Per the official Hansken architecture documentation:
  "The Project-service is responsible for CRUD operations on projects,
   stored in Postgresql."
  "Postgresql is used to store stateful data of the connected services.
   So, for instance, it stores user preferences and project metadata."
  — Source: https://learning.hansken.org/docs/architecture.html#project-service

PostgreSQL stores lightweight relational records:
  - Case/project definitions (name, investigators assigned, status)
  - User preference settings
  - Access control records (which investigators access which cases)
  - Task scheduling state (Lobby scheduler metadata)

PostgreSQL data volume is negligible compared to evidence storage.
A generous estimate is 0.1–0.5 TB total for even very large deployments.


7B. POSTGRESQL REPLICATION FACTOR
------------------------------------
PostgreSQL achieves redundancy via:
  a. Streaming replication (primary + standby replica) — factor: × 2
  b. Logical replication or Patroni HA — factor: × 2 or more
  c. In a Kubernetes deployment: persistent volume with snapshot + backup.

Standard HA PostgreSQL for Hansken = 1 primary + 1 synchronous standby
  Replication factor: × 2
  WAL archive / backup overhead: + 50% additional on top of live data

  Total PostgreSQL multiplication factor: ≈ × 3 (including backups)


7C. POSTGRESQL STORAGE CALCULATION
-------------------------------------
  PostgreSQL data volume estimate:         ~1 TB (very generous upper bound)
  HA replication (×2):                     ~2 TB
  WAL + backup overhead (×1.5):            ~3 TB
  ─────────────────────────────────────────────────────────────────────────
  TOTAL POSTGRESQL CAPACITY REQUIRED:              ~3 TB
  ─────────────────────────────────────────────────────────────────────────
  Note: PostgreSQL is negligible relative to the other tiers. High-
  performance SSD storage is required (IOPS-sensitive), but the volume
  is small. Include in HA storage planning, not raw capacity planning.
