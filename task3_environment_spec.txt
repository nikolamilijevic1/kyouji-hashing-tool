SECTION A — NUMBER OF ENVIRONMENTS

2. RECOMMENDED ENVIRONMENT COUNT: 3
--------------------------------------
Hansken is delivered as a packaged platform (Helm charts on Kubernetes), but
it still requires a structured environment pipeline for the following reasons:

  WHY DO YOU NEED MORE THAN JUST PRODUCTION?

  a) EXTRACTION PLUGIN DEVELOPMENT & TESTING
     Hansken supports custom extraction plugins, packaged as OCI (Docker)
     container images. Plugins must be developed, validated, and tested before
     being introduced to production evidence processing. A non-production
     environment is required for this safely.
     Source: https://learning.hansken.org/docs/plugins/

  b) PLATFORM UPGRADES & PATCH VALIDATION
     Hansken receives periodic updates from NFI. These must be tested against
     your specific configuration (LDAP integration, storage backends, custom
     plugins) before applying to production, or you risk breaking live
     investigations.

  c) INVESTIGATOR TRAINING
     New investigators need a sandbox with realistic (but non-sensitive) data
     to learn the platform without risk to live case data.

  d) INTEGRATION TESTING
     If Hansken is integrated with other upstream systems (evidence intake
     systems, case management, chain of custody tools), those integrations
     must be validated before production deployment.

  RECOMMENDED 3-ENVIRONMENT PIPELINE:

  +-------------+-------------------+------------------------------------------+
  | Environment | Short Name        | Primary Purpose                          |
  +-------------+-------------------+------------------------------------------+
  | Production  | PROD              | Live forensic investigations by          |
  |             |                   | authorized investigators. Full HA.       |
  |             |                   | Real evidence data. Max security.        |
  +-------------+-------------------+------------------------------------------+
  | Staging /   | STAGE / UAT       | Pre-production validation: platform      |
  | Acceptance  |                   | upgrades, plugin acceptance, integration |
  |             |                   | testing. Mirrors PROD architecture.      |
  |             |                   | Uses sanitized/synthetic data.           |
  +-------------+-------------------+------------------------------------------+
  | Development | DEV               | Plugin development, investigator         |
  | / Test      |                   | training, configuration experiments.    |
  |             |                   | Reduced resources. No HA required.       |
  +-------------+-------------------+------------------------------------------+

  NOTE: If budget constraints require reducing to 2 environments, the minimum
  viable combination is PROD + STAGE/UAT. Development can be done on local
  workstations using Docker/Minikube (Hansken supports local developer
  environments via its SDK).

SECTION B — ARCHITECTURE OF EACH ENVIRONMENT
================================================================================

3. PRODUCTION (PROD) — HIGH AVAILABILITY (HA)
-----------------------------------------------
  Architecture Type:  FULL HA (Active-Passive with automatic failover)

  WHY HA IS REQUIRED FOR PRODUCTION:
  - Evidence processing is time-sensitive for active investigations.
  - Forensic data at rest is irreplaceable; storage failures without redundancy
    risk permanent data loss.
  - Chain-of-custody integrity requires uninterrupted audit log collection.
  - A production outage directly impacts law enforcement investigative capacity.

  HA Requirements by Component:
  +-----------------------+--------------------------------------------------+
  | Component             | HA Design                                        |
  +-----------------------+--------------------------------------------------+
  | Kubernetes Control    | 3 control plane nodes (etcd quorum — requires    |
  | Plane                 | odd number ≥ 3 for leader election)              |
  +-----------------------+--------------------------------------------------+
  | Kubernetes Workers    | Minimum 3 worker nodes (pods rescheduled on      |
  |                       | node failure via Kubernetes node controller)     |
  +-----------------------+--------------------------------------------------+
  | Apache Hadoop (HDFS)  | RF=3 replication across ≥3 DataNodes on ≥2 racks|
  |                       | NameNode in HA mode with standby NameNode        |
  +-----------------------+--------------------------------------------------+
  | Elasticsearch         | 3-node cluster (1 primary + 1 replica shard;     |
  |                       | master-eligible quorum of 3 for split-brain      |
  |                       | prevention)                                      |
  +-----------------------+--------------------------------------------------+
  | PostgreSQL            | 1 primary + 1 synchronous standby (Patroni       |
  |                       | recommended for automatic failover)              |
  +-----------------------+--------------------------------------------------+
  | Keycloak              | 2+ instances in active-active cluster mode       |
  |                       | sharing PostgreSQL backend                       |
  +-----------------------+--------------------------------------------------+
  | NATS JetStream        | NATS cluster with 3 nodes (Raft consensus)       |
  +-----------------------+--------------------------------------------------+
  | Apache Kafka          | 3-broker cluster + Zookeeper 3-node quorum       |
  +-----------------------+--------------------------------------------------+
  | Ingress / Load Bal.   | 2 load balancer nodes (active-passive)           |
  +-----------------------+--------------------------------------------------+

  RTO Target (Recovery Time Objective):   < 15 minutes
  RPO Target (Recovery Point Objective):  < 1 hour (based on backup frequency)
  [PENDING — OI-2]: Confirm RTO/RPO targets with management.

4. STAGING / ACCEPTANCE (STAGE) — LIMITED HA
----------------------------------------------
  Architecture Type:  LIMITED HA (Resilient but not fully redundant)

  Staging mirrors Production architecture but at reduced scale:
  - Single control plane node (or 3-node if shared cluster with namespaces)
  - 2–3 worker nodes (no full rack redundancy)
  - Hadoop RF=2 (node failure tolerable; rack failure not)
  - Elasticsearch: 2-node cluster (functional but not fully quorum-safe)
  - PostgreSQL: primary only, with scheduled backup; no live standby
  - NATS / Kafka: single broker (not clustered)

  Purpose: Catch configuration and integration issues before PROD, not to
  simulate production-level SLA. Downtime in this environment is acceptable.

  Data policy: Sanitized or synthetically generated forensic data ONLY.
  No real evidence data may reside in the Staging environment.

5. DEVELOPMENT / TEST (DEV) — NO HA
--------------------------------------
  Architecture Type:  NO HA (Single-node or minimal cluster)

  Dev is a minimal footprint environment:
  - Single Kubernetes node or 2-node cluster (1 control + 1 worker)
  - Hadoop: single DataNode (RF=1 or RF=2, data loss acceptable)
  - Elasticsearch: single node, single shard, no replica
  - PostgreSQL: single instance, no replication
  - NATS: single node
  - Kafka: optional (single broker if needed for plugin testing)

  Alternative for individual developers:
  - Local workstation using Minikube or Docker Desktop + kind cluster
  - Hansken SDK supports local plugin development and unit testing without
    a full cluster deployment.

  Data policy: Synthetic / anonymized test data ONLY. No case data.

8. LOCAL STORAGE PER SERVER
-----------------------------
  NOTE: HDFS and Elasticsearch use local attached storage on their dedicated
  nodes. All other services (Hansken core, Keycloak, NATS, Kafka) use
  Kubernetes Persistent Volumes backed by a shared storage array or SAN.

  PRODUCTION:

  Node Role          | Local Storage Type  | Local Storage Size  | Purpose
  ─────────────────────────────────────────────────────────────────────────────
  Control Plane      | SSD (OS + etcd)     |  500 GB             | OS, etcd DB
  App Workers        | SSD (OS + ephemeral)|  500 GB             | OS, tmp
  Extraction Workers | SSD (OS + scratch)  |  1 TB NVMe          | OS + large
                     |                     |                     | extraction
                     |                     |                     | scratch space
  HDFS DataNodes     | HDD (data) +        | 12× 16 TB HDD       | Raw evidence
                     | SSD (OS + journal)  | + 2× 1 TB SSD       | HDFS data
                     |                     | = ~194 TB raw/node  | = 582 TB raw
                     |                     |                     | total (HDFS)
  Elasticsearch      | NVMe SSD (indices)  | 4× 7.68 TB NVMe     | Trace index
  Nodes              | + SSD (OS)          | + 1× 1 TB SSD       | high IOPS
                     |                     | = ~30 TB/node       |
  ─────────────────────────────────────────────────────────────────────────────

  SHARED PERSISTENT VOLUME STORAGE (for app workloads):
  - Provisioned via SAN, NFS, or Ceph RBD
  - Minimum 50 TB shared storage pool for app-layer PVs (PostgreSQL WAL,
    Kafka log segments, NATS stream data, Keycloak DB)
  - SSD/NVMe-backed for PostgreSQL and NATS (latency-sensitive)
  - SAS/HDD acceptable for Kafka logs (throughput-oriented)

9. OPERATING SYSTEM REQUIREMENTS
----------------------------------
  Hansken runs on Kubernetes. The OS requirement is for the Kubernetes
  node OS (the host OS on each server, not within containers).

  RECOMMENDED OS: Ubuntu 22.04 LTS (Jammy Jellyfish) — Long Term Support
                  OR Red Hat Enterprise Linux (RHEL) 9.x

  Comparison:
  +------------------+-----------------------------+---------------------------+
  | Criterion        | Ubuntu 22.04 LTS            | RHEL 9.x                  |
  +------------------+-----------------------------+---------------------------+
  | Container Runtime| containerd (default)        | CRI-O (OpenShift) or      |
  |                  | Full Docker support         | containerd                |
  | Kubernetes       | Full compatibility          | Full compatibility         |
  | Support          | (kubeadm, Rancher, etc.)    | (OpenShift preferred)     |
  | Security         | AppArmor (default)          | SELinux enforcing (default)|
  | Support Lifecycle| 5 years LTS (to 2027)       | 10 years (to 2032)        |
  | Cost             | Free (Canonical support     | Paid subscription          |
  |                  | subscription optional)      | required per socket        |
  | Forensic/Gov use | Common in open deployments  | Standard for high-sec gov  |
  |                  |                             | and law enforcement        |
  +------------------+-----------------------------+---------------------------+

  RECOMMENDATION:
  - If your organization is a government / law enforcement agency with
    existing RHEL licensing: use RHEL 9.x for all node types.
  - If your organization is more flexible: Ubuntu 22.04 LTS is equally
    capable and reduces licensing cost.
  - For HDFS DataNodes and Elasticsearch nodes specifically: ensure
    kernel supports XFS filesystem (both RHEL and Ubuntu do).

  OS per Server Type Summary:
  +-----------------------------+--------------------------------------------+
  | Server Role                 | OS                                         |
  +-----------------------------+--------------------------------------------+
  | Kubernetes Control Plane    | Ubuntu 22.04 LTS  OR  RHEL 9.x            |

9B. SERVER TYPE: VM vs. BARE METAL
-------------------------------------
  RECOMMENDATION: Virtual Machines (VMs) on existing hypervisor infrastructure
  for App Workers and Control Plane nodes; consideration of Bare Metal for
  HDFS DataNodes and Elasticsearch Nodes.

  Rationale:
  +------------------------------+-------------------------------------------+
  | VM (all nodes)               | Bare Metal (storage/compute nodes)        |
  +------------------------------+-------------------------------------------+
  | + Faster provisioning        | + No hypervisor overhead on I/O           |
  | + Easier snapshot/backup     | + Maximum storage throughput              |
  | + Simpler HA failover        | + Better HDFS DataNode performance        |
  | + Infrastructure re-use      |   (critical for 500 TB/yr ingestion)      |
  | - Hypervisor overhead 4–18%  | - Higher management complexity            |
  | - Hypervisor is a new SPOF   | - No live migration / snapshotting        |
  +------------------------------+-------------------------------------------+

  HYBRID APPROACH (Recommended):
  - Kubernetes Control Plane, App Workers: VMs (flexibility + HA)
  - HDFS DataNodes, Elasticsearch Nodes: Bare Metal (raw I/O performance)
  - Extraction Workers: VMs with NVMe passthrough, or Bare Metal if budget
    allows

11. BACKUP AND DISASTER RECOVERY (DR) PLAN
--------------------------------------------
  PRODUCTION BACKUP STRATEGY:

  +---------------------+------------------+----------------------------------+
  | Component           | Backup Method    | Frequency / Retention            |
  +---------------------+------------------+----------------------------------+
  | Hadoop HDFS         | HDFS Snapshots   | Daily snapshot; 30-day retention |
  | (raw evidence)      | + off-cluster    | Weekly full copy to DR site or   |
  |                     | replication      | cold storage. Evidence is        |
  |                     |                  | immutable; primary copy must be  |
  |                     |                  | protected at all times.          |
  +---------------------+------------------+----------------------------------+
  | S3 Object Store     | S3 Versioning    | S3 versioning enabled.           |
  | (derived data)      | + cross-bucket   | Cross-bucket replication to DR   |
  |                     | replication      | site. Derived data is            |
  |                     |                  | re-generatable from HDFS if lost |
  |                     |                  | (lower priority than HDFS).      |
  +---------------------+------------------+----------------------------------+
  | Elasticsearch       | Snapshots to S3  | Daily ES snapshot to S3/object   |
  | (trace indices)     | repository       | store. 14-day retention.         |
  |                     |                  | Indices can be re-indexed from   |
  |                     |                  | HDFS/S3 if needed (slow).        |
  +---------------------+------------------+----------------------------------+
  | PostgreSQL          | pg_dump /        | Continuous WAL archiving (PITR). |
  | (metadata)          | pg_basebackup    | Daily base backup. 30-day WAL    |
  |                     | + WAL archiving  | archive retention.               |
  +---------------------+------------------+----------------------------------+
  | Keycloak            | PostgreSQL backup | Covered by PostgreSQL backup.    |
  | (auth state)        | + realm export   | Additionally, weekly Keycloak    |
  |                     |                  | realm export (JSON) stored in    |
  |                     |                  | version control.                 |
  +---------------------+------------------+----------------------------------+
  | Kubernetes State    | etcd snapshot    | Automated etcd snapshot every    |
  | (cluster config)    | (Velero)         | 6 hours via Velero. Backed up    |
  |                     |                  | to S3/object store.              |
  +---------------------+------------------+----------------------------------+
  | Helm Values /       | Git repository   | All Helm values files, custom    |
  | Config              |                  | configs, and manifests in Git.   |
  |                     |                  | Git repo itself must be backed   |
  |                     |                  | up externally.                   |
  +---------------------+------------------+----------------------------------+

  DISASTER RECOVERY TIERS:
  - Tier 1 (RTO < 15 min):  Kubernetes pod restarts, HDFS NameNode failover,
                              PostgreSQL Patroni automatic failover.
  - Tier 2 (RTO < 4 hours): Full node failure recovery. Node replacement +
                              Kubernetes pod rescheduling + HDFS re-replication.
  - Tier 3 (RTO < 24 hours): Full cluster loss. Recovery from backup
                              (PostgreSQL PITR, ES snapshot, HDFS snapshot).

12. AUTHENTICATION
-------------------
  Hansken uses a layered authentication and authorization model built into
  its architecture. No additional external SSO gateway is required to start.

  AUTHENTICATION STACK:

  +---------------------+----------------------------------------------------+
  | Layer               | Technology & Configuration                         |
  +---------------------+----------------------------------------------------+
  | Identity Provider   | Keycloak (OIDC / OAuth2)                           |
  | (Primary)           | Bundled with Hansken Helm chart by default.        |
  |                     | Issues JWT access tokens to authenticated users.   |
  +---------------------+----------------------------------------------------+
  | User Directory      | OpenLDAP (bundled default)                         |
  |                     | OR Active Directory (recommended for enterprise)   |
  |                     | Keycloak federates to LDAP/AD via User Federation. |
  |                     | Investigators do NOT have local Hansken accounts;  |
  |                     | all identity management is centralized.            |
  +---------------------+----------------------------------------------------+
  | Multi-Factor Auth   | Enforced at Keycloak authentication flow.          |
  | (MFA)               | Options:                                           |
  |                     |   - TOTP (RFC 6238): Google Authenticator, Authy   |
  |                     |   - WebAuthn / FIDO2: hardware security keys       |
  |                     |   - SMS OTP: supported but NOT recommended for     |
  |                     |     law enforcement (SIM-swap risk)                |
  |                     | [PENDING — OI-10]: Confirm MFA method required.    |
  +---------------------+----------------------------------------------------+
  | Authorization       | Role-Based Access Control (RBAC) within Hansken.  |
  |                     | Roles assigned in Keycloak and propagated via JWT: |
  |                     |   - INVESTIGATOR: read/search access to cases     |
  |                     |   - CASE_MANAGER: create/manage cases             |
  |                     |   - ADMIN: full platform administration            |
  |                     | Case-level access control: investigators only see  |
  |                     | cases they are explicitly assigned to.             |
  +---------------------+----------------------------------------------------+
  | Transport Security  | TLS 1.2 minimum (TLS 1.3 preferred) on all HTTPS  |
  | (In-Transit)        | endpoints. Mutual TLS (mTLS) for internal gRPC    |
  |                     | service-to-service communication via Istio/Envoy  |
  |                     | service mesh (Hansken uses this internally).       |
  +---------------------+----------------------------------------------------+
  | Encryption at Rest  | Hansken encrypts evidence images via the Keystore.|
  |                     | Encryption keys are per-case. Node-level disk      |
  |                     | encryption (LUKS / BitLocker equivalent) should    |
  |                     | be applied at the OS level by the infrastructure  |
  |                     | team for full defense-in-depth.                    |
  +---------------------+----------------------------------------------------+

  ACTIVE DIRECTORY INTEGRATION NOTE:
  If your organization uses Microsoft Active Directory, Keycloak can federate
  directly to AD via LDAP. This means investigators log in with their existing
  Windows/agency credentials. This is the recommended approach for a
  centralized storage initiative with existing AD infrastructure.
